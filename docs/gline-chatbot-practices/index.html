前提となる目的と制約

本設計は G-LINE 採用サイトに埋め込むチャットボットを対象としています。ヒアリングで確認された以下の要件・制約をすべて満たすことを前提に、10案を評価します。

主要な要件（抜粋）

  • 会社理解 → 応募・面接予約への導線化（右下ウィジェット）
  • 会社概要・募集要項・面接予約導線・軽い日常相談までを扱う
  • 未公開／機密情報・給与交渉の断定回答は禁止
  • 代表（荒牧氏）の熱意ある話し方を再現（A案口調）
  • 24時間受付、回答不能時は info メールへエスカレーション
  • 会話ログは90日保存（匿名化後に分析活用）
  • FAQ・募集情報の更新は代表と採用担当が担う

先に結論：G-LINE への推奨構成

RECOMMENDED

ハイブリッド 3層構成：決定木UI → 静的FAQ全文検索 → ビルド時AI事前生成 Q&A

①ボタン選択で8割カバー（会社概要・募集要項・面接予約）、
②テキスト質問はブラウザ内Fuse.jsで静的FAQを検索（料金ゼロ）、
③Claude で月1回オフライン生成した代表口調の Q&A JSON を検索対象に追加（運用時APIコール無し）。
回答不能時は「info メールへ」導線で必ず人にエスカレーション。

運用時の月額APIコスト：0円（ビルド時のみ数十円〜数百円の Claude 利用）。 非エンジニアは faq.json または Notion（連携可）を編集するだけで反映。

最小実装サンプル（Fuse.js）

// faq.json を読み込み、あいまい検索する最小例
const faq = await fetch('/faq.json').then(r => r.json());
const fuse = new Fuse(faq, {
  keys: ['question', 'keywords'],
  threshold: 0.35,        // あいまい度
  includeScore: true
});

function answer(userText) {
  const hits = fuse.search(userText);
  if (!hits.length || hits[0].score > 0.35) {
    return escalateToEmail();  // No.7 の導線
  }
  return hits[0].item.answer;
}

リスクと対策

RISK

押さえておくべき5つの落とし穴

  • ①幻覚リスク：生成AIを運用時に使う案（No.4）は、会社情報を創作する可能性。要件「会社情報を勝手に断定・創作しない」に抵触するため、運用APIは原則使わない
  • ②機密情報の漏洩：FAQに未公開情報を混ぜない。PRレビューで代表・採用担当の承認を必須化
  • ③個人情報の保存：90日ルール／氏名・電話・メールは自動マスク／ログは匿名化してから分析
  • ④給与・条件交渉：回答禁止ワードリストを用意し、検知したら即座に No.7 へ切替
  • ⑤キャッシュで古い募集要項：Service Workerにバージョンキーを含め、募集更新時に必ず無効化

追補：生成AI × RAG 版「社長の分身」を作る

方針転換（2026-04-18）：要件「社長に答えてもらっているように感じる」を最優先するため、生成AI + RAG をコアに据える。ただし将来の乗り換えコストをゼロに近づけるため、モデルは差し替え可能な抽象化層で包み、週次で自動監視する。

DECISION

採用モデル：Gemini 3.1 Flash-Lite（2026-04時点）

  • 料金：$0.25/1M input, $1.50/1M output（Claude Haiku 4.5比 −72%）
  • 月額見込み：約 $2〜$5（採用ボット想定・キャッシュ活用後）
  • 強み：1Mコンテキスト（代表の本を丸ごと投入可）／Context Caching／RAG文脈に忠実でハルシネーション低／Google Cloud でデータ残留地域選択可
  • 代替候補：GPT-5.4 nano（$0.20/$1.25）、Nova Lite、Ministral 3 8B

切替可能設計の4本柱

1

抽象化層

Adapter パターン or LiteLLM で全プロバイダ統一API化

2

設定一元化

config/llm.yaml 1ファイルで全てを制御

3

週次自動監視

GitHub Actions で毎週月曜に新モデル検知

4

評価スイート

週次ワークフロー（自動化フロー）

  1. 毎週月曜 09:00 JST：GitHub Actions が起動
  2. Gemini 公式 API /v1beta/models から最新モデル一覧を取得
  3. 現行設定 (config/llm.yaml) と差分チェック → 新モデル候補を抽出
  4. 候補モデルに対して Eval スイート 50問 を自動実行
  5. スコアが閾値（0.85）以上 かつ 現行より安ければ合格
  6. 合格したら 切替用 PR を自動作成（タイトル：「LLM切替提案: <新モデル> (cost -X%)」）
  7. Slack に週次レポート投稿（新モデル／価格変動／推奨アクション）
  8. 人間は PR レビューして merge するだけ

Adapter 層（lib/llm.ts 抜粋）

interface LLMProvider {
  chat(msgs: Message[], opts?: Options): Promise<Response>
}

const providerMap = {
  google:    GeminiProvider,
  openai:    OpenAIProvider,
  anthropic: AnthropicProvider,
}

export async function chatWithFallback(msgs, opts) {
  const cfg = loadConfig()
  for (const m of [cfg.current, ...cfg.fallback_chain]) {
    try { return await new providerMap[m.provider](m).chat(msgs, opts) }
    catch (e) { console.warn(`[${m.provider}/${m.model}] failed, next...`) }
  }
  throw new Error('All providers failed')
}

リスクと対策（追補）

  • モデル乗り換え時の口調のブレ → Eval の tone_check 項目で A案らしさを数値化し、閾値割れで不合格
  • Preview モデルの突然の廃止 → fallback_chain で GA モデルを必ず含める（gemini-3-flash, gpt-5.4-nano）
  • API キー漏洩 → GitHub Secrets 管理、ブラウザ直叩き禁止（Cloudflare Workers 経由で中継）
  • 評価基準の陳腐化 → Eval ケースを月次で追加（未回答 Issue から補充する運用）

追補2：データベース設計（Neon PostgreSQL 単体構成）

Supabase / Cloudflare D1+R2 / BigQuery / Firestore 等を全て検討した結果、Neon PostgreSQL 単体が「個人情報保護・RAG・分析・GDPR対応・データ増加耐性・既存知見流用」を最もバランス良く満たす結論に至りました。

DECISION

採用：Neon PostgreSQL（pgvector 付き・東京リージョン）

  • 料金：無料 0.5GB（採用ボット実データ10年分）／超過後 $19/月 10GB
  • pgvector で RAG も同じDB（層分散なし）
  • Neon HTTP Driver で Cloudflare Workers から直接叩ける
  • ブランチングで開発/ステージング/本番を無料で分離
  • Row Level Security + 列暗号化で個人情報を厳格保護
  • 業界標準 PostgreSQL。pg_dump で何処へでも移行可能

スキーマ設計（7テーブル）

applicants     -- 応募者情報（氏名/メール/電話 = 暗号化列, RLS保護）
appointments   -- 面接予約（applicants へ FK）
conversations  -- 会話ログ（匿名化 session_id, 90日 TTL 論理削除）
rag_chunks     -- RAG チャンク + embedding vector(768) HNSW

escalations    -- 人間引き継ぎキュー（info メール通知トリガ）

RLS ポリシー（個人情報保護の要）

  • ロール分離：app_public（書込のみ）/ app_admin（全権限）/ app_analytics（個人情報マスクビューのみ閲覧）
  • applicants テーブル：app_public は INSERT のみ、SELECT/UPDATE は app_admin のみ
  • conversations：session_id はハッシュ化済みで app_analytics も閲覧可能、ただし個人特定情報は含まない運用
  • 削除要求対応：DELETE FROM applicants WHERE id = $1 で関連レコード CASCADE 削除 → 物理削除完了

RAG の仕組み（pgvector HNSW）

代表の本・自叙伝・HP・募集要項を 500トークン単位でチャンク化 → Gemini text-embedding-004 で 768次元に埋込 → rag_chunks テーブルに保存。検索時はコサイン類似度 Top5 を取得しプロンプトに注入。

-- RAG 検索クエリ（Top5 近傍）
SELECT chunk_text, 1 - (embedding <=> $1::vector) AS similarity
FROM rag_chunks
ORDER BY embedding <=> $1::vector
LIMIT 5;

月次で GitHub Actions monthly-rag-rebuild.yml が代表の原稿を再埋込 → テーブル差替。

90日ログ削除（Neon は pg_cron 非対応のため Actions で）

Neon は 2026年時点で pg_cron をサポートしていないため、GitHub Actions の日次 cron（daily-purge.yml）で物理削除します。

-- 90日超の会話ログを物理削除（匿名なのでそのまま DELETE）
DELETE FROM conversations WHERE created_at < NOW() - INTERVAL '90 days';

-- 個人情報は論理削除→物理削除の 2段階
UPDATE applicants SET deleted_at = NOW() WHERE requested_deletion = TRUE;
DELETE FROM applicants WHERE deleted_at < NOW() - INTERVAL '30 days';

Neon の弱点（正直評価）

  • 無料枠 0.5GB：Supabase の 500MB と同等。超過時は $19/月
  • サーバーレスのコールドスタート：最大 500ms 遅延（採用ボットは秒単位応答なので影響軽微）
  • AWS ベース：軽度のロックインあり、ただし pg_dump で即退避可能
  • pg_cron 非対応：定期処理は GitHub Actions で代替（本雛形で対応済み）
